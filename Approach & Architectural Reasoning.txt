Approach & Architectural Reasoning
Core Philosophy: Cascade Before You Call
The single most important design decision is the tiered healing cascade: 6 layers, each attempting healing in order of cost. Rule-based mutations (XPath variants, CSS attribute anchors, shadow DOM pierce) resolve roughly 72% of failures with zero LLM cost and sub-millisecond latency. The LLM is a precision scalpel used only on the remaining 28%, not a hammer for every broken locator.
This is what separates an enterprise architecture from a toy integration.

Why This Beats Every Other Approach
Naive LLM healers send the full DOM to an LLM on every failure. At 48K tokens for a Salesforce record page, at scale across 100 projects, that is economically and latency-wise catastrophic. Our DOMCompressor reduces that to ~400 tokens — a 99% reduction — by pruning invisible nodes, collapsing single-child chains, and retaining only the semantic neighbourhood ±3 levels around the failed element.
Pure rule-based healers (existing open-source tools like Healenium) have no intelligence for semantic drift — when a button's text, position, and attributes all change simultaneously, rules fail completely. The LLM layer handles this.
Visual-only healers are slow and expensive for every call. We use vision LLM only as a last resort for elements that have no stable DOM anchor — typically SF chart tiles, KPI widgets rendered in canvas, or custom SVG components.

Salesforce-Specific Intelligence: Why It Demands Special Treatment
Salesforce is not a normal web application. Three things make it uniquely hostile to conventional locators:
First, Lightning Web Components use closed shadow roots. Standard Selenium findElement cannot pierce LWC shadow boundaries. The SFShadowDOMResolver uses JavaScript-level pierce traversal and maps elements to component-stable identifiers (sf-data-id, data-component-id) which survive re-renders.
Second, Salesforce regenerates numeric ID suffixes (:0, :1, :238) on every page load. Any locator using these IDs breaks immediately on the next run. The XPathVariantEngine strips these suffixes before any cache lookup, and the LLM prompt explicitly instructs the model to produce component-relative XPaths rather than absolute ID-based paths.
Third, Flexipage layout drift is triggered by admins, not developers. An admin rearranges a record page, and 40 locators break overnight with no code change. The DriftDetector tracks per-page failure rates and fires a preemptive re-scan job when drift is detected, rather than discovering failures during a live test run.

Token Efficiency: The Engineering That Makes It Economical
The DOM compression pipeline runs four sequential pruning passes before any LLM call:

Remove <script>, <style>, and <link> nodes
Strip nodes with display:none, visibility:hidden, or aria-hidden=true
Collapse single-child intermediate nodes (common in React/LWC wrappers)
Retain only ±3 ancestor/sibling levels around the failed element

The resulting structure is serialized as a minimal JSON tree — not HTML — which is 30–40% more token-efficient than HTML for equivalent structural information.
For parallel test suites, the LLMGateway batches up to 8 simultaneous heal requests into a single LLM call with a structured JSON response. This cuts per-heal API overhead by roughly 85% during high-parallelism runs.

Scalability Across 50–100 Projects
The TenantIsolator gives every project a namespaced Redis partition, independent LLM quota, and a separate Grafana dashboard. Projects cannot bleed healing data into each other — a critical requirement when the same Selenium framework serves 50 different product teams.
The LLMGateway supports provider-level fallback chains per project: a cost-sensitive regression suite can be configured to use a smaller model, while a critical smoke suite gets a frontier model. When a provider throttles, the gateway fails over to the next in the chain automatically.
The VaultPromoter is what makes this system genuinely self-improving: every successfully healed locator is promoted back into the primary alternative set with a Bayesian confidence score. Over weeks of test runs, the cache hit rate climbs — the LLM call rate falls — and the system becomes cheaper and faster the longer it runs.

Implementation Path
Start with L1 (interception) and L2 (cache + rule-based healing) — these alone recover 70%+ of failures and can be built without any LLM dependency. Add L3 (LLM engine) with DOMCompressor for the semantic gap. Deploy L5 (learning loop) to let the system improve automatically. L4 (visual) and L6 (observability) round out the production-grade system.
